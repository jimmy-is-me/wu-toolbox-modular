# v3.7.2 — Contained tabs and reliable product deadlines

- Exclude dashboard module tabs from generic settings-tab selectors. The generic `:is(#wutm-media,...)` selector previously had ID specificity, overriding dashboard padding/minimum height and pushing selected buttons outside the frame. Tests now check actual button boundaries at five widths, not only the outer heights.
- Preserve `_expiration_datetime`, the classic product publish-box field and sortable list column. Parse strict valid local dates using `wp_timezone()` and absolute timestamps, never PHP's default timezone or offset timestamps.
- Repair missing or incorrect alarms even when the deadline is unchanged. Validate before cancelling old alarms, preserve deadlines on errors, treat omitted fields as no change, and make cleared/rescheduled events harmless.
- Past deadlines get an immediate alarm and a shutdown callback after WooCommerce's save lifecycle. Execution rechecks deadline/type/status, guards recursion, saves through product CRUD, records the latest result, clears completed metadata/alarms and notifies common cache integrations.
- Every five minutes, a background recovery task checks at most 20 due published products with a five-second processing budget. It is established from admin requests; no catalogue scan is added to ordinary frontend requests. Module/plugin disabling clears the recurring task.
- Expired product and variation purchase filters deny buying even when cron is late. An uncached single-product request also attempts overdue processing and returns 404 outside previews. Existing full-page/CDN caches may bypass PHP and must be purged by their configured integrations; exact wall-clock background execution still requires working host cron/loopback traffic.
- Product UI shows site timezone, queued/missing/overdue state, latest result, and a warning when internal cron is disabled. Unit fixtures cover permission/nonce, timezone, invalid input, cancellation, stale events, repair, failures, purchase gating and bounded recovery. Disposable real WordPress/MySQL tests exercise native cron/storage/status hooks through a WC CRUD fixture, not a customer's live store.

The reported public product URL could not be retrieved by the read-only tool. No claims are made about that site's installed version, cron configuration or current database status, and no production settings/products were changed.
