# v3.8.0 — WU NewebPay payment/shipping and restored EZPAY invoice

- Add one WU-branded card/Toolbox submenu after ECPay in 電商第三方金物流. Four sections cover service switches, NewebPay merchant configuration, NewebPay CVS shipping and the complete retained EZPAY invoice schema. The standalone ECPay invoice module stays removed; the existing official ECPay integration is unchanged.
- Import the NewebPay subset from the pinned reference `3735fa63d1add98521b18f9311bad4a7b2dc1632`; retain GPL attribution and isolate classes/constants, options, gateway/shipping IDs, callbacks and browser assets. Preserve six primary payment types, six split installment variants, native shipping-zone settings, coupon/minimum/weight/class shipping costs, payment instructions and order metadata. No unrelated payment provider or general checkout customization is bootstrapped.
- Restore the v3.7.8 private Guzzle/PSR/InvoicePorter/Metabox invoice dependency graph. Retain original EZPAY settings, checkout fields, order calculations, manual/automatic operations and account output. Fresh invoice activation defaults off; an explicit saved activation value is not changed. A saved old module-card flag can provide the new card's initial state without writing options. NewebPay payment/shipping remain off until explicitly configured.
- Harden AES padding/malformed ciphertext handling and timing-safe signature validation; bind decrypted callback to configured merchant, known generated merchant order, total/currency, payment or supported COD shipping, and paid transaction. Keep bounded attempt and duplicate fingerprints on the order. Use atomic per-order database locks with compare/delete stale takeover and owner-safe release. Do not downgrade paid orders on stale failure callbacks or repeat payment-complete events for exact duplicates.
- Preserve original request-building bodies, wrapping invoice issue/void in a shared lock and preventing a second issue for an existing invoice number. Keep manual AJAX permission/nonces, safe errors, unblock behavior and no automatic retries. Do not print raw exception data or log complete new payment payloads.
- The WU shipping browser adapter only adds/removes its own selected-view CSS class. It does not clear store IDs, logistics fields, personal fields, or another provider's values.
- Source checksums distinguish mechanical WU renaming from four explicit payment/browser security adaptations; invoice source preservation reverses named wrappers and the fresh-site default only. CI includes native WordPress 6.8.3 / WooCommerce 9.0.2 fixture payment forms, signed mock callbacks, database locks, mocked invoice payload/meta and duplicate protection, plus foreign Guzzle 7/PSR 2 load orders and desktop/mobile tests.
- Real merchant APIs are not called by tests. Classic checkout and legacy order storage are the supported combination; no end-to-end Blocks/HPOS invoice compatibility or actual merchant issuing/refund/shipping certification is claimed. Merchant sandbox acceptance and reconciliation remain required.

References: [invoice workflow](https://docs.wpbrewer.com/wpbr-ezpay-einvoice), [pinned source](https://github.com/zenbuapps/woomp/tree/3735fa63d1add98521b18f9311bad4a7b2dc1632). See [setup and limitations](NEWEBPAY-EZPAY.md).
